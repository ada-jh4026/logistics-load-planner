# 设计决策 v0.1
这些是本项目的默认设计，不是官方强制技术要求。后续模型按此实现，避免重复架构讨论。

## D01 范围
单仓、单日、每车一趟，回仓；每个门店全部箱件作为一个分配单元，同一门店不拆车、不重复访问。不引入取货、混合温层、多仓、实时地图、账户体系。

## D02 数据粒度与单位
一个boxes元素就是一个实际箱件，数量由元素个数表达。门店平面坐标以km计；车厢和箱件以整数mm计；重量kg；费用元；时间为当天零点起分钟，可为小数。几何坐标为整数，面接触不算碰撞。浮点容差1e-6仅用于时间、重量及费用计算。

## D03 技术分层
后端默认Python，纯函数核心与Web框架隔离；Web层采用FastAPI，单进程+单工作线程串行求解，内存任务字典只用于本地比赛原型。重启丢任务必须说明，不声称生产高可用。B01验证环境并固定实际依赖版本。
前端默认React+TypeScript，Vite开发，Three.js做3D；如同学已有项目可保留其可运行技术栈，但须实现同一接口，并在F01记录决定。框架版本由实际可安装环境确定并提交锁文件，不凭记忆写“最新版本”。
不需要数据库、消息队列、容器集群或外部地图服务。CORS仅放行本地前端地址；默认后端127.0.0.1:8000，前端127.0.0.1:5173，端口占用可改但同步启动说明。
智能体服务（调度助手）是独立 FastAPI 进程，目录 `agent/`，默认127.0.0.1:8001，与 `backend/` 零代码耦合，只通过 JSON 协议相连；前端经 Vite 代理同时访问 `/api`（求解器）与 `/agent`（智能体）。模型接口走 OpenAI 兼容协议，默认 DeepSeek，可替换为企业私有化模型。

## D04 优先级
P0是数据验证、实际求解、独立约束检查、真实界面联调、实验和运行文档。3D逐步高亮属于核心展示；平滑动画和视觉装饰可延期。截止前至少90分钟冻结功能。
智能体线（A01–A03、F07）为 P1，由前端线并行承担，不占主线时间；其模板模式保证没有模型密钥时核心流程照常。A04 与模型模式的效果打磨为 P2。

## D05 几何模型
后门为x=0，x向车头、y横向、z向上。仅允许绕z轴0/90度旋转。门口视为完整车厢截面，无轮包或门框厚度。
箱件落地或由单个非易碎箱顶面完整承托。不实现跨多箱桥接、重心、振动或材质抗压模型。这是保守几何模型，不声称真实搬运全物理可行。
卸货限定沿-x方向水平抽出；不得穿过其他箱体，不得抽走仍承托其他箱的底箱。每件抽出后重新检查剩余箱的承托。
装货使用最终卸货动作的逆序；若要宣称装货可执行，必须用逆序校验。

## D06 目标与失败
先最大化完整服务门店数，再最大化服务箱数，再最小化费用，再最小化里程；最后按ID固定排序打破并列。固定费用已体现增车成本，不另用不明确权重。
只返回通过校验的执行计划。不能通过的整车方案可以作为诊断候选保存，但其货物全部回到未分配池，不计配送完成。
找不到布局记SEARCH_EXHAUSTED；单件所有允许朝向均超过所有车厢可记BOX_TOO_LARGE。前者不等同数学不可行证明。
局部packer发现当前车尺寸不合，仅记录当前车的OUT_OF_BOUNDS诊断；其他车型能放时不得把门店最终原因写为全局BOX_TOO_LARGE，必须保留换车修复机会。

## D08 智能体层原则
- 分工：LLM 负责理解与表达（自然语言指令 → 受控补丁；真实结果 → 有据解释；两次方案 → 对比叙述），确定性求解器负责全部调度决策，独立校验器负责可信保障。LLM 不输出坐标、路线、车辆分配或箱件去向。
- 人在环：智能体生成的补丁以字段级 diff 展示，用户确认后才提交 `/api/solve`；智能体自身不调用求解接口。
- 受控补丁：只允许 AGENT_CONTRACT.md 列出的白名单字段与操作；模型按实体 ID 表达意图，服务端解析为 RFC 6902 补丁并用协议模型校验。
- 证据绑定：模型只看服务端确定性推导的事实表；输出文本中的每个数字必须能在事实表中匹配，否则重试一次后回退模板，并在 warnings 记录。
- 可降级：无密钥、超时、输出不合格均回退为规则/模板模式，HTTP 不返回 5xx。
- 数据边界：发送给模型的只有事实表与实体摘要，不含坐标与凭据；密钥只在 `agent/.env`，仓库只提交 `.env.example`。
