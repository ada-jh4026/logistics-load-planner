# 下一轮优化执行方案：协同证据与修复过程

编写日期：2026-10-10。基准提交：`b84a592`。**本文件是执行方案；完成情况以 board 和真实证据为准。** O01、O02 已在本地实施并验收，见 `artifacts/evidence/O01.md`、`artifacts/evidence/O02.md` 和 `docs/conflict-results.md`；O03–O06 仍为后续建议/交接。此前写“尚未运行”的段落属于计划形成时的历史背景。

## 1. 目标与现状

主张：让配送计划在发车前通过“装得下、送得准、卸得出”的可执行性检查，并根据装载冲突反馈修复调度方案。

当前事实：
- 原有 21 次实验已在 I02 重跑、校验并推送；每种方法跨 7 案服务 180/180 店。
- coupled 相对 greedy 的费用改善为 4.73%–19.61%，但与 sequential 费用完全相同，协同修复未触发。不能把这些降本归因于修复。
- `backend/solver.py::_try_relocate` 找到第一个可行搬移就返回；`solve_coupled` 全覆盖即停止，当前不做全覆盖后的降本搜索。
- `tests/test_coupled.py` 的 C10 是单个长箱由小车转大车，证明机制可运行，但不足以证明多约束协同价值。
- 当前成功修复的历史没有完整保留；最终 `diagnostics` 不能作为完整回放记录。
- 原任务只剩 I04 最终验收；新增优化完成后必须重做受影响的 I04 检查。

本轮必须得到：可信的冲突实验、可追溯的修复事件、一个使用真实求解响应的演示。即使实验没有收益，也交付真实结果和机制边界。

本轮范围不包括：更换框架、多仓、多日、真实道路接入、生产账号体系、强化学习、大规模算法重写。不要为展示收益削弱基线、独立校验或约束。

## 3. O01：修复记录与消费协议（必须）

### 3.1 实现前先统一协议

下面是明确的设计建议，**当前运行接口尚无此字段**。主线实现前写入 CONTRACT/DECISIONS/CHANGES 和接口样例，然后以 CONTRACT 为唯一依据。

建议在 `Result` 增加可选 `repair_trace`，缺省/旧记录为 `null`，不替换现有 `diagnostics`。后端 Pydantic、`agent/schemas.py` 的独立镜像、`frontend/src/protocol/contract.ts` 的 Zod 模型必须一致。不能仅修改后端后就宣称向后兼容：旧消费者可能拒绝或丢弃新字段，应先升级消费者或协调一起重启联调。

建议 RepairTrace 最小结构：

| 字段 | 语义 |
|---|---|
| `version` | 记录结构版本，建议整数 1 |
| `status` | `not_needed` / `repaired` / `partially_repaired` / `unresolved` / `budget_exhausted`；定义优先级，预算退出优先，成功程度另由指标表示 |
| `initial_metrics`、`final_metrics` | 初始/最终**已验证的执行方案**指标；不把失败候选计入服务或费用 |
| `initial_routes` | 初始已验证路线，用于重建接受事件前的状态；失败整车不混入此处 |
| `attempted_count`、`accepted_count` | 确实评估的候选数、确实采用的状态转换数；生成但未评估不算尝试 |
| `events` | 稳定排序的真实事件数组 |
| `truncated`、`omitted_count` | 日志限长是否截断、未保留事件数；总计数不能因截断变化 |

每个事件建议包含：`event_id`、`iteration`、`action`（pack_failed / relocate / reorder）、`outcome`（detected / rejected / accepted）、`store_ids`、`box_ids`、`source_vehicle_id`、`target_vehicle_id`、`reason_code`、`message`。未知实体使用空数组/null，不能猜测冲突箱。

接受事件额外保存：前后全局 score/metrics，以及变化车辆的已验证 `routes_before`、`routes_after`；空列表可表示原来没有可执行路线。可用初始路线和接受事件逐步重建最终方案。拒绝事件保存实际检查结果，不必保存全部失败布局。

分数统一为（未服务门店数，未服务箱数，费用，里程），字典序比较。展示“前后费用差”时必须注明服务集合是否一致。

第一版不要求展示非法箱体的完整 3D 布局。只有后端确实保存了失败候选布局且明确标注“诊断候选”时，前端才能绘制它；不能根据错误文案补造箱体位置。

### 3.2 实现注意事项

- 每次 `_evaluate` 不能清空整个搜索历史；日志独立于最佳结果维护，返回时附到最终快照。
- 接受动作必须经过时间窗、装载、卸货与独立校验，并确实成为当前采用方案；“尝试成功”不等于“采用”。
- `SEARCH_EXHAUSTED` 只表示启发式未找到，不能写“数学上装不下”。当前车放不下与所有车型都放不下要区分。
- 日志限长优先保留所有接受事件和关键冲突；拒绝事件可限制保存数量。记录截断不影响求解选择或准确计数。
- 普通案例明确返回 `not_needed`；旧响应缺字段显示“此记录未提供修复过程”，二者不可混淆。
- 预算、取消与异常仍遵循现有协议，保留最佳已验证结果，不为补日志额外继续长时间搜索。

### 3.3 验收

用实际 C10 求解证明事件从冲突到接受可串联，引用 ID 均存在；接受事件最终重建结果与返回 routes/metrics 一致。覆盖无需修复、未解决、预算退出、日志截断、旧 JSON 无字段五种情况。主线交付真实 request/response/validation；人工 UI 样例 `is_mock=true`，不进入实验计分。

输出：`artifacts/evidence/O01.md`；约定协议样例放 `docs/playbook/examples/repair/`，与旧三组样例隔离。真实事件样例另存 `artifacts/repair-trace/`。

## 4. O02：冲突实验和公平对照（必须）

### 4.1 案例设计

先构造以下三类最小开发案例；核实目标冲突确实出现后再参数化。不是要求算法必须赢。

1. **组合几何冲突**：单箱均可放入相关车型、总重量和体积通过必要检查，但多箱形状、承托或易碎约束使某个分组难以装载；另一分配有明确可行见证。避免只复制超长箱换大车。
2. **卸货顺序冲突**：固定一个可装入的布局，确认其指定顺序被卸货校验拒绝；再检查端到端 packer 是否能自己避开冲突。只有真实管线出现了该冲突，才称为“触发修复案例”。若现有 packer 总能规避，按机制校验案例报告，不能伪造触发率。
3. **时间窗与装载冲突**：至少一个看似能解决装载的调度动作因时间窗被拒绝，另一个动作通过全部校验；另配资源不足的未解决控制例。

建议正式扩展规模：三类各 5 个固定种子变体（11、22、33、44、55），加 2 个无需修复控制、2 个有明确约束矛盾的控制，共 19 个案例。开发最小例与正式变体分开标识。若某一类不能成立，明确缩减并记录原因，不能硬凑 19 个或宣称已覆盖。

生成规则、参数范围、种子、案例分类在运行对比前写入 manifest 并落盘。所有预定种子结果保留；重复输入记录哈希并说明，不把完全相同的输入算独立证据。若调参，另设开发种子，正式种子只用于最后评估；观察正式结果后再次调参必须披露。

可行见证可手工构造或由独立小规模枚举获得，统一交给独立校验器检查。不能靠 coupled 成功筛选“好案例”。不可行控制必须有明确理由（例如任何车辆都装不下某单件）；一般启发式失败不得标为不可行。

数据建议放 `data/conflict_cases/`；批量实验文件不必全部加入前端案例选择器，只把代表案例按现有发现机制接入，避免列表过长。每案有独立 metadata/witness，不能把额外字段塞进严格 SolveRequest。

### 4.2 对照方法

保留 greedy、sequential、coupled，并增加一个**仅实验使用**的 `sequential_reinsert` 对照（名称可调整，但必须记录定义）：

- 从与 sequential 相同的初始路线和配载结果开始，保留成功的路线。
- 对失败整车中的门店及其他未分配门店，按最晚收货时间、ID 稳定排序。
- 将整店箱件尝试插入现有成功路线或未使用车；候选按费用增量和稳定 ID 排序，每次均重新验证；采用首个可行插入。
- 不移动已经成功分配的门店、不调换既有门店相对顺序；失败门店明确保留。它代表简单的失败后补救，不应被故意削弱。
- 所有方法使用同一 packer、校验器、费用模型、输入、时间预算。若新增单箱车型预检查，应共享于适用方法，或在实验表里单独消融，不只给 coupled 使用。

第四方法通过 benchmark 内部适配器运行；`options.method` 的公开三值枚举先不扩张。实验清单另记 `variant` 和实际入口，不能伪装为 coupled 响应，也不能让脚本报告“调用了第四个 API 方法”。若必须扩接口，先另行记录明确的契约变更。

初次对比保留当前 coupled，标明代码提交；O03 采用增强后另存结果与 variant。不得覆盖 I02 或首次结果。正式比较不得混用不同代码版本的不明实现。

### 4.3 指标与证据

- 单案：服务门店 ID 集合、门店/箱件完成数、最终校验、是否全覆盖、车辆数、费用、耗时、终止原因。
- 修复：是否实际触发、尝试次数、接受次数、初始/最终服务差、是否达到全覆盖；触发率分母为全部相应案例，成功率同时写清分母。
- 費用改善只在同案相同已服务门店集合、双方校验通过、基线费用大于零时计算；其他为 null 并解释，不把服务更多但成本更高写为降本失败或成功。
- 分开汇报三类冲突、无需修复控制、不可行控制；失败、超时、无增益和倒退全部保留。
- 计时使用相同机器与配置；条件允许时预热后重复 3 次报中位数与范围。仅一次则明确单次观察，不据三种规模宣称近似线性复杂度。
- 沿用 request/response/validation、data_hash、环境、代码版本、方法配置、原始计时；额外方法的文件结构和语义在 manifest 说明。

输出：`artifacts/benchmarks/conflict-<stamp>/`、`artifacts/evidence/O02.md`、独立冲突结果报告 `docs/conflict-results.md`。此报告只有实际运行后才创建为“结果”。

## 5. O03：按证据增强算法（有条件）

先阅读 O02 失败与候选日志，再决定采用哪些动作：

### A. 预算内择优搬移（优先）

当前 `_try_relocate` 首个可行即返回。改为先做廉价筛选并按费用增量稳定排序，在预算允许时比较有限个可行候选。比较最终已验证分数，按 ID 打破并列；预算耗尽返回最佳已验证快照。候选上限有配置/记录，不能为了收集候选耗尽全部预算后没有可返回结果。

构造“第一个可行目标更贵、后续目标更优”的明确回归，并与 first-feasible 做同输入消融。若只改善费用而覆盖相同，按可比成本规则计分。

### B. 车内相邻门店交换（仅在顺序冲突成立时）

在失败车辆上枚举有限相邻交换，检查完整时序、重新装载和卸货；通过且全局分数改善才采用。保持门店不拆分、访问唯一。不能因为新顺序能装载就忽略迟到。

只有 O02 确实出现该问题才实施；如果重排无收益，报告无收益，不强制保留复杂度。不要在本轮顺带增加全覆盖后的任意降本搜索、无限多步搬移或双向换单。

其他风险：一次只搬一个门店可能无法解决需连续多步调整的失败路线。记录为能力边界；不要偷偷放宽约束或把未验证中间态作为可执行结果。如果它是唯一主要瓶颈，另写小范围方案再取舍。

输出：`artifacts/evidence/O03.md`（或明确的跳过记录）；增强版本的实验和消融结果独立保留。

## 6. O04：Claude 的界面与解释任务（必须）

界面增加“协同修复”区域，包含：是否触发、初始/最终服务数、尝试/采用次数、实际冲突与接受动作时间线。拒绝尝试折叠展示；选中事件联动车辆/门店/箱件高亮。修复前后视图只读取快照，不自行补算布局。

必须覆盖：旧记录无 trace、无需修复、成功、部分成功、未解决、预算退出、截断。字段不存在时显示未提供，不显示“0 次修复”伪装确定事实。失败候选若没有坐标，只呈现诊断文本和已有实体高亮。

智能体扩充确定性事实表：提供发生过的动作、实体引用、验证结果、统计与可比性，不发送完整坐标给模型。模板模式也能解释。模型不得把 rejected 描述为 accepted，不得在 not_needed 状态称“协同修复降本”；数字匹配通过也不等于动作语义正确，动作解释优先使用确定性文本，LLM 只做辅助概述。

建议不增加新的 explain focus 或新端点：先在现有总览/本车解释加入修复事实，避免不必要的 API 扩张。确需变化先同步 AGENT_CONTRACT 和类型。

验收至少包括：旧 JSON、无修复、真实成功修复、未解决、预算退出；模板/FakeLLM 离线测试；有密钥时做真实模型联调并记录 mode，无密钥不阻塞核心演示。数字、实体和动作逐项核对，截屏和控制台记录落盘。

输出：`artifacts/evidence/O04.md`、`artifacts/demo/repair/`，以及给主线的协议兼容/启动/案例/尚未完成列表。

## 8. 执行者交接格式

每阶段记录：ID、状态、实际完成、变更文件、协议影响、真实命令与退出结果、证据路径、代码版本、未完成项、下一阶段。协议交接额外给：字段定义、缺省行为、真实和样例响应位置、消费者必须更新的路径。

对用户的结果报告必须区分：已实现、已验证、实验未支持的主张、可选后续优化。提交/推送与官方提交分别描述，不自动发布作品。用户仅要求本轮写方案；切换模型后按新的执行指令开展实现。
