# 系统架构

城市配送智能配载原型由三个独立进程组成，只通过两份 JSON 协议相连。任何一层都可以单独替换或部署。

```
┌──────────────────────────────────────────────────────────────────────┐
│ 交互层  frontend/   Vite + React + TypeScript + Three.js    :5173     │
│   案例选择 / JSON 导入 / 运行求解 / 车辆与路线 / 3D 车厢 / 逐步卸货    │
│   调度助手面板：解释 · 一句话改约束 → 字段级 diff → 人确认 · 前后对比   │
└───────────────┬──────────────────────────────────┬───────────────────┘
                │ /api/*  CONTRACT v0.1              │ /agent/*  AGENT_CONTRACT v0.1
┌───────────────▼──────────────────┐   ┌───────────▼───────────────────┐
│ 决策层  backend/  FastAPI  :8000  │   │ 智能体层  agent/  FastAPI :8001 │
│   models  协议模型与输入校验       │   │   facts     事实表（确定性推导）  │
│   routing 路线构造（贪心 / 插入）  │   │   explain   解释 + 数字核对       │
│   packing 3D 配载启发式           │   │   interpret 指令 → 白名单补丁     │
│   unloading 卸货可行性 / 装货逆序  │   │   compare   指标差值 + 可比性     │
│   repair + solver 协同修复循环    │   │   llm       OpenAI 兼容客户端     │
│   validation 独立校验器           │   │             默认 DeepSeek，可换   │
│   jobs 单线程任务队列             │   │   templates 无模型时的规则文本    │
└──────────────────────────────────┘   └───────────────┬───────────────┘
                                                        │ 只发事实表与实体摘要
                                                        ▼
                                              OpenAI 兼容模型接口（可私有化）
```

## 职责边界

| 层 | 做什么 | 不做什么 |
|---|---|---|
| 决策层 | 所有调度决策：分车、排序、3D 摆放、卸货顺序；每个返回的方案都经独立校验器重算一遍约束 | 不读模型输出；不信任任何外部给的「可行」 |
| 智能体层 | 把结果解释给人、把人的话变成受控补丁、比较两次方案 | 不输出坐标、路线、分配；不调用求解接口；不接触坐标与凭据 |
| 交互层 | 展示响应字段；编排「指令 → 确认 → 提交 → 对比」 | 不重算路线或布局；不直连模型 API |

这条边界是方案进入企业环境的安全论证：大模型可以替换、可以离线，调度结果的正确性不依赖它。

## 数据流

1. 用户选择案例或导入 JSON（前端用 zod 按协议校验，错误逐条提示）。
2. `POST /api/solve` 入队，`GET /api/jobs/{run_id}` 每 500 ms 轮询到终态；响应含路线、到站时刻、箱件坐标、卸货步骤、未配送原因、独立校验结果、指标。
3. 前端按返回坐标绘制 3D；按 `unload_steps` 逐步播放。
4. 解释：前端把请求与响应发给 `/agent/explain`；服务端推导事实表 → 模型生成 → 数字核对 → 不通过回退模板。
5. 指令：`/agent/interpret` 返回意图、RFC 6902 补丁、补丁后的完整请求、被拒操作；前端展示 diff，用户确认后再走第 2 步。
6. 对比：新结果到达后前端调用 `/agent/compare`；服务端按「同服务门店集合 + 均通过校验」判定费用是否可比。

## 求解器内核（backend/）

- **路线构造**：门店按最晚收货时间排序；`greedy` 尾部追加、`sequential` 全位置插入 + 两轮 2-opt。只检查载重、总体积、时间窗这些必要条件。
- **3D 配载**：按卸货逆序、非易碎优先、体积降序放置；候选位置由已放箱边界生成；允许水平 90° 旋转；承托必须由单个非易碎箱完整托住。
- **卸货校验**：逐站逐件沿后门方向水平抽出，扫掠空间不得与其他箱相交，不得先抽承托中的底箱。装货指引为卸货逆序。
- **协同修复**（`coupled`）：某车装不下或卸货被挡时，把冲突门店移到其他已有车的最佳插入位或未用车，重新装载并校验，按（未服务门店数，未服务箱数，费用，里程）字典序保留最佳快照。
- **独立校验器**：对最终方案重算分配完整性、车辆唯一、时间窗、载重、边界、碰撞、承托、易碎、卸货阻挡、指标；不信任求解器自报的 `valid`。
- **预算**：单调时钟 + 迭代上限，预留 10% 给最终校验；超时返回最佳已验证快照。

## 智能体内核（agent/）

- **事实表**：从请求与响应确定性推导；单车利用率、等待与松弛时间按请求重算。模型只看事实表，不看坐标。
- **数字核对**：提取回答中的时刻、百分数、带单位数字，逐个在事实表中匹配（带单位只在同类事实里找）；首轮不通过带提示重试一次，再不通过回退模板并写入 `warnings`。
- **受控补丁**：模型按实体 ID 输出意图；服务端解析下标、校验白名单（时间窗、服务时长、易碎、旋转、求解选项、增减车辆）、应用后用协议模型与范围规则校验；越权与非法操作进入 `rejected_ops`。
- **降级**：无密钥、超时、异常、输出不合格都回退模板，HTTP 不返回 5xx。

## 规模与性能（记录机器：Windows 11，Python 3.12）

| 案例 | 门店 / 箱件 / 车辆 | 单次求解 |
|---|---|---|
| small | 10 / 36 / 4 | 约 15–30 ms |
| standard | 30 / 112 / 12 | 约 50–80 ms |
| stress | 60 / 236 / 24 | 约 140–200 ms |

求解在当前规模远未触及时间预算；瓶颈会首先出现在协同修复的候选枚举（每个冲突门店 × 每辆车 × 每个插入位 × 一次重新装载）。扩展思路：按地理分区并行求解、候选位置索引化、修复循环只重算受影响车辆（已实现）。

## 部署形态

- 开发：三进程同机，前端 Vite 代理转发。
- 生产：前端静态产物由网关托管，`/api` 与 `/agent` 反向代理到两个服务；求解服务可按队列横向扩展（任务存储换为外部队列）；智能体服务指向企业内网的 OpenAI 兼容模型。
- 与企业系统对接：订单（OMS）→ SolveRequest 的 stores / boxes；车辆主数据（TMS）→ vehicles；输出的路线与装载方案回写 TMS / 现场 PDA。本仓库只定义 JSON 协议，不含任何企业系统适配代码。
