# 城市配送智能配载 · logistics-load-planner

「AI重构产业·架构师大赛」物流赛道作品。面向连锁门店城市配送：把订单、车辆、时间窗输入，输出每辆车的配送路线、每个箱件在车厢里的三维摆放、按到站顺序的卸货步骤，所有方案经独立校验器重算约束；一个调度助手智能体负责把结果解释给调度员、把一句话指令变成受人确认的修改、比较调整前后的方案。

> 当前版本运行在**模拟数据**上（字段与真实业务一致，数值为程序生成）。所有收益数字来自本仓库可复现的实验，不代表真实企业效果。

## 1. 业务场景与痛点

传化物流的城市配送场景：一个中心仓每天向几十家门店（赛题以连锁药店为例）配送几百个 SKU，调度员要在车辆容量、货物装载条件、门店交付时效的多重约束下，同时决定派哪些车、每辆车跑什么顺序、货物怎么装、到店怎么卸。赛题列出的五个痛点里，我们把**配载与配送计划缺乏协同**作为核心：总体积装得下不等于箱子真能摆进去；路线合理也不等于到站后前面的货取得出来。这两件事现在只能靠人到现场才发现。

目标用户是中心仓调度员与现场装卸人员。使用流程：导入当日订单与可用车辆 → 运行求解 → 查看路线、3D 装载与卸货步骤 → 对不满意的地方用一句话改约束（某门店只能下午收货、某车今天不出车）→ 确认后重算并对比 → 把装卸作业单给现场。

## 2. 核心方案

```
交互层  frontend/   调度工作台：KPI 行 / 路线 / 3D 车厢 / 卸货动画 / 协同修复时间线与快照回放 / 三法对比 / 作业单打印 / 调度助手
决策层  backend/    路线构造 → 3D 配载 → 卸货可行性 → 协同修复 → 独立校验
智能体  agent/      事实表 → 证据绑定解释 / 一句话 → 受控补丁 / 方案对比
```
三个进程只通过两份 JSON 协议相连（`docs/playbook/CONTRACT.md`、`docs/playbook/AGENT_CONTRACT.md`）。详细架构见 [docs/architecture.md](docs/architecture.md)。

**求解器**：门店按最晚收货时间排序后做路线构造（简单贪心尾插、全位置插入 + 2-opt 两种策略，按增量费用比较）；每辆车做确定性 3D 配载：同规格箱件按卸货逆序填充；**混合规格箱件按到站逆序分区构造**，末站靠车头、先送靠后门，每次放置都检查从后门进入的扫掠路径，允许水平旋转，承托须由单个非易碎箱完整托住；再逐站逐件模拟沿后门方向抽出，检查是否被挡、是否抽走了承托中的底箱。装不下或卸不出时，**协同修复**在预算内对最多 8 个搬移候选做完整重装载与独立校验、择优采用，再用剩余预算对未配送门店逐店恢复；每次检测、拒绝、采用都记入 `repair_trace`，采用事件带修复前后的已验证路线快照。最终方案由独立校验器重算全部约束，不信任求解器自报的结果。

**智能体**（LLM 不做调度决策）：
- 解释：服务端从请求与响应确定性推导「事实表」，模型只看事实表；回答中可识别的数字（阿拉伯与常见中文数字、倍率、百分数、时刻）按单位和所属实体在事实表里逐个核对，推算出的合计、借用全局数字描述单车等都算未匹配，触发重试，再不通过回退到模板文本。核对是文本层面的拦截，不证明语义正确（边界见 `docs/limitations.md`）。
- 指令：模型把「S07 下午两点后才能收货，V02 不出车」翻成按 ID 的意图；服务端检查白名单（时间窗、服务时长、易碎、旋转、求解选项、增减车辆），生成 RFC 6902 补丁并用协议校验；越权修改（改箱件尺寸、改车辆载重、改门店坐标）被明确拒绝并说明；多子句指令里没被识别的子句、提到了却没生成修改的实体，都会在警告里列出，不会被静默丢掉。前端把补丁显示为字段级 diff，**人确认后**才提交求解。
- 对比：按「服务门店集合相同且均通过校验」判定费用是否可比；不可比时只讲覆盖变化，不给降本百分比。
- 修复事实：事实表从 `repair_trace` 确定性转述发现了什么冲突、采用了几次搬移、可执行门店从多少到多少；旧响应写「未提供记录」，未触发写「未触发」，被拒的尝试不会被说成已采用。
- 无模型密钥时全部能力以模板模式运行，核心流程不中断。

## 4. 数据来源

- **模拟数据**：`scripts/generate_cases.py` 用固定随机种子生成，门店平面坐标、时间窗、箱件尺寸重量、两种车型。案例在 `data/cases/`：small（10 店 36 箱 4 车）、standard（30 店 112 箱 12 车）、stress（60 店 236 箱 24 车）各 3 / 3 / 1 个种子，以及 c01 / c02 / c03 / c07 四个验收案例。正常案例按「已知可行」构造，保证至少存在一个全配送方案。
- **手工界面样例**：`docs/playbook/examples/`，响应 `is_mock=true`，只用于前端开发与协议校验，页面上标「演示数据」。
- **距离与时间**：门店间为平面欧氏距离，固定车速换算；不是真实道路测算，页面与解释文本均注明。
- **人工环节**：验收案例的期望值由人工手算（`docs/playbook/ACCEPTANCE.md`）；指令测试集（`agent/tests/data/instructions.jsonl`）的 20 条指令与期望补丁由人工编写。
- 晋级后的真实业务数据将按赛事方规则另行接入，本仓库不含任何企业数据。

## 5. 测试结果与实验

### 5.1 求解器基准（主线 B15 修正版，`artifacts/benchmarks/corrected-*/`，Windows 11 / Python 3.12）
三种方法共用同一数据、同一独立校验器、同一时间预算。21 条记录全部 100% 服务门店、全部通过独立校验、终止原因均为搜索完成。每条记录保留请求、响应与校验文件。

| 案例（门店 / 箱件） | 简单贪心 | 先路线后装载 | 配载与路线协同 | 协同相对贪心 |
|---|---|---|---|---|
| small-11（10 / 36） | 2 车 912.3 元 | 2 车 869.2 元 | 2 车 869.2 元 | −4.7% |
| small-22 | 2 车 960.8 元 | 2 车 873.4 元 | 2 车 873.4 元 | −9.1% |
| small-33 | 2 车 1,089.3 元 | 2 车 940.2 元 | 2 车 940.2 元 | −13.7% |
| standard-11（30 / 112） | 6 车 2,492.0 元 | 5 车 2,003.2 元 | 5 车 2,003.2 元 | −19.6% |
| standard-22 | 5 车 2,346.8 元 | 5 车 2,176.6 元 | 5 车 2,176.6 元 | −7.3% |
| standard-33 | 5 车 2,040.0 元 | 5 车 1,834.9 元 | 5 车 1,834.9 元 | −10.1% |
| stress-44（60 / 236） | 9 车 3,829.2 元 | 8 车 3,263.9 元 | 8 车 3,263.9 元 | −14.8% |

费用改善率只在「服务门店集合相同且均通过校验」时计算（`scripts/benchmark.py`）。体积利用率：standard 70–77%，stress 92%。单次求解耗时：small 15–50 ms，standard 60–130 ms，stress 200–330 ms（同一机器，含独立校验）。

如实说明两点：
1. 在这批「已知可行」同规格数据上装载从未失败，协同修复一次也没触发，因此「协同」与「先路线后装载」结果相同。上表的费用改善来自路线构造差异，**不能归因于协同修复**。协同修复的作用见 5.2 的冲突实验与 5.3 的混合箱件实验。
2. 首轮实验（`artifacts/benchmarks/{small,latest,stress}/`）中插入式构造比贪心多用一倍车辆，根因是候选按整车费用而非增量费用比较。两名成员分别独立定位到同一原因（`artifacts/probes/`、`artifacts/evidence/B15-correction.md`），修正后重跑得到上表。首轮记录保留但不再适用于当前代码。

### 5.2 合成冲突实验（主线 O02/O03，`artifacts/benchmarks/o02-conflict-20261010/`、`o03-ranked-20261010/`，`docs/conflict-results.md`）
19 个预登记案例：5 个组合几何冲突、5 个几何与时间窗联动、5 个卸货机制控制、2 个无需修复控制、2 个确证不可行控制。另加一个**仅实验内部**的简单补救基线 `sequential_reinsert`（从顺序法已验证方案起，只重新插入未分配门店）。

| 组 | greedy | sequential | sequential_reinsert | coupled |
|---|---|---|---|---|
| 组合几何冲突（5 案，每案 2 店） | 0/10 店 | 0/10 店 | 10/10 店 | 10/10 店，5 次真实采用 |
| 几何 + 时间窗联动（5 案，每案 3 店） | 5/15 店 | 5/15 店 | 15/15 店 | 15/15 店，5 次真实采用 |
| 卸货机制控制（5 案） | 预置坏布局均被 UNLOAD_BLOCKED 拒绝；四法端到端都直接找到合法布局，修复触发 0 次 | | | |
| 确证不可行控制（2 案） | 四法均 0 服务，没有被伪装成已配送 | | | |

如实结论：协同修复能把「不可执行」恢复为「可执行」，并且过程可在 `repair_trace` 逐条核对；但在这些案例上它与简单补救基线的覆盖和费用**完全相同**，没有证据表明当前协同策略优于「失败后重新插入」。O03 的预算内择优搬移只在一个开发回归案上比首可行策略便宜 41%，与补救基线仍持平。

### 5.3 混合箱件实验（主线 H01，`artifacts/benchmarks/hetero-*/`，`docs/heterogeneous-results.md`）
把基准案例的箱件从统一 500 mm 立方体换成 8 种混合纸箱（含长条与大件，更接近药店 SKU 外箱）。修复前三种方法在多门店路线上几乎全部装载失败（standard、stress 均 0 店）；分区式配载与逐店恢复之后：

| 案例（门店 / 箱件） | greedy | sequential | sequential_reinsert | coupled（修复后） |
|---|---|---|---|---|
| small-11-mixed-1 / -2（10 店） | 0/10 | 0/10 | 10/10，1,334 / 1,255 元 | **10/10（repaired）**，1,334 / 1,255 元 |
| standard-11-mixed-1 / -2（30 店） | 0/30 | 0/30 | 30/30，2,987 元 / 29/30，2,804 元 | **30/30（repaired）**，3,282 / 3,014 元 |
| stress-44-mixed-1 / -2（60 店） | 0/60 | 0/60 | 32/60，2,976 元 / 36/60，3,208 元 | **60/60（repaired）**，6,895 / 6,758 元 |
| 留出集 6 案（未参与调试） | | | | 全部 100%，repaired |

如实结论：**收益是覆盖率，不是费用。** 服务集合相同时协同与补救基线费用打平（small）或更高（standard-11-mixed-1 为 +9.9%，约 10%）；stress 上协同以更多车辆换来全覆盖（60/60 对 32–36/60），服务集合不同，费用不可比。修复后 stress 用 19–22 辆车、体积利用率约 20%，仍偏保守。留出集 6 案与开发集来自同一生成机制、只换种子，全部通过只说明修复不依赖特定开发种子，不能推断到真实 SKU 分布。同规格基准（5.1）在修复后表现不变。

### 5.5 端到端
三服务同机，浏览器自动化（修正后的求解器）：small-11 真实求解（2 车 869.2 元）→ 模型解释（核对 23 个数字）→ 指令「V02 今天不出车」→ 字段级 diff「车辆 V02：可用 → 移除」→ 确认重算 → 自动对比：10 → 10 店，2 → 2 车，869.2 → 919.2 元，服务集合相同、费用可比，**上升 5.8%**。少一辆可选车让方案变贵，系统如实报告上升，不做任何美化。截图与日志见 `artifacts/evidence/F05.md`、`F07.md`、`I01.md`。协同修复面板在五种状态（无需修复 / 修复成功 / 部分修复 + 截断 / 未解决 / 预算退出）上用主线真实输出验收，可切换采用事件的修复前后布局快照（`O04.md`、`artifacts/demo/repair/`）。页面还提供「对比三种方法」（同一请求串行求解三法并排，费用只在可比时给百分比）与按车的可打印现场装卸作业单（`UI-polish.md`、`artifacts/demo/ui/`）。演示脚本当前使用 standard-11：5 车 2,003.2 元 → 「V02 和 V04 今天都不出车」→ 5 车 2,053.2 元，费用可比 **+2.5%**（`artifacts/demo/flow-standard-11/`）。

## 7. 当前限制

- 单仓、单日、每车一趟；箱形货物；固定时间窗；不建模实时路况、多仓、异形物体、材质承重、重心。
- 3D 配载是保守启发式：「未找到布局」不等于数学上不可行；体积利用率不代表空间最优。
- 距离为平面直线，不是道路网络。
- 协同修复在同规格基准上未被触发（5.1）。合成冲突实验上与简单补救基线覆盖、费用完全相同（5.2）；混合箱件实验上 small 持平、standard 多覆盖 1 店或费用高约 10%、stress 覆盖 60/60 对 32–36/60 但车辆更多（5.3）。其价值是可执行性、覆盖率与可追溯，不是降本。
- 混合箱件下仍不允许跨箱共同承托，修复后 stress 规模车辆数偏多。
- 智能体不做多轮对话；指令白名单之外的修改需要在页面或 JSON 中手工完成。
- 单进程串行求解，队列上限 8；未做并发与持久化。

## 8. 工程化与落地路径

**规模**（记录机器：Windows 11，Intel Core Ultra 9 185H，32 GB，Python 3.12；预算 `time_limit_ms=10000`）：

| 数据 | 方法 | small（10 店） | standard（30 店） | stress（60 店） | 终止原因 |
|---|---|---|---|---|---|
| 同规格箱件（5.1） | coupled | 31–47 ms | 78–125 ms | 296 ms | 全部 completed |
| 混合箱件（5.3，基准记录） | coupled | 2.0–2.9 s | 6.5–6.7 s | 13.6–18.2 s | 全部 completed |
| 混合箱件（5.3，基准记录） | sequential_reinsert | 1.2–2.3 s | 8.4–9.0 s | 14.5–15.9 s | 出现 time_limit / iteration_limit |

同规格数据上耗时随门店数增长大致成比例，但只有 3 个规模点、且混合箱件下耗时增长更快，「近似线性」只能算待验证假设。混合箱件的 stress 记录超过名义预算，因为预算只在修复循环入口检查，不约束单次完整重装载；今日同机通过服务接口重跑 stress-44-mixed-1 为 5.6 s。瓶颈在协同修复的候选枚举（每个冲突门店 × 每辆车 × 每个插入位 × 一次重新装载）。扩展思路：按地理分区并行、候选位置索引、任务队列换为外部队列横向扩展求解进程（接口不变）。

**资源与成本（实测 + 估算，分开标注）**：实测——求解服务常驻约 40 MB，混合箱件 stress 求解峰值约 100 MB；智能体服务约 80 MB；前端静态产物主包 394 kB（gzip 120 kB），3D 视图 950 kB 单独分包按需加载；一次解释或指令调用向模型发送 7–36 千字符（small → stress，含事实表），实测单次 1–3 s。估算——按 DeepSeek 公开价格，一次调用在分币级；若指向企业内网模型则无按量费用。维护责任：求解器与校验器（Python 纯计算，无外部依赖）、智能体提示与白名单（随业务字段变化需同步）、前端（随协议版本变化需同步），三者通过两份 JSON 协议解耦，可分别由不同人维护。

**对接**：输入侧 OMS 订单 → `stores` / `boxes`，TMS 车辆主数据 → `vehicles`；输出侧路线与装载坐标回写 TMS，装卸作业单下发现场 PDA。本仓库只定义 JSON 协议，不含企业系统适配代码。

**模型与数据安全**：智能体的结构化输入只含事实表与实体摘要（ID、时间窗、尺寸、费用），不含坐标、不含凭据；但调度员在页面输入的自由提问与指令会**原样**进入模型提示，用户若自己写入坐标或其他业务信息，这些内容同样会发出。因此真实业务数据阶段应把模型接口指向企业内网私有化部署（接口为 OpenAI 兼容协议，传化已有本地化部署的 DeepSeek），并在网关层控制出网；未经书面许可不得把真实数据发往外部平台，去掉坐标不等于其他字段可以外发。模型不可用时系统降级为模板模式，调度结果的正确性不依赖模型。

**实施路径**：① 历史订单离线回放，用独立校验器与人工方案对照；② 调度员影子试用，系统方案与人工方案并行、只看不用；③ 人工确认后执行，逐步扩大自动化范围。每一步的指标口径与本仓库实验一致（完成率、车辆数、费用、利用率、准时率、卸货阻挡）。

**关键障碍**：真实车厢的门框、轮包、绑扎点等结构；货物的实际可堆叠层数与抗压；门店收货的实际作业时长。这些都是晋级后需要真实数据才能标定的参数。
