# 城市配送智能配载 · logistics-load-planner

面向「AI重构产业·架构师大赛」物流赛道，用两天完成一个可运行、可演示、可验证的城市配送智能配载原型。本仓库也保存了可供不同模型接力执行的完整开发路线。

> **当前阶段：执行手册已准备，业务代码尚未开始。** 仓库中的方案、接口样例和验收规格不代表功能已实现，也不代表已经取得优化收益。最新事实以 [当前进度](docs/playbook/STATE.md) 和 [任务状态表](docs/playbook/board.json) 为准。

## 1. 我们准备解决什么问题

场景是一个中心仓向多家门店配送：车辆、货物尺寸与重量、门店时间窗以及卸货顺序共同影响方案是否可执行。

计划实现的业务闭环：

**导入订单与车辆 → 分配车辆和配送路线 → 检查实际装载与卸货 → 调整冲突方案 → 展示3D布局与操作步骤 → 对比基线结果。**

重点是配载与路线之间的反馈：总体积够，不代表箱件实际装得下；路线合理，也不代表到站后货物拿得出来。系统应识别这些问题，并尝试调整摆放、配送顺序或车辆分配。

两天内限定为单仓、单日、箱形货物、固定时间窗、有限车辆。先使用明确标注的模拟数据；不扩展实时路况、多仓、复杂物理仿真或完整企业管理后台。具体假设见 [设计决策](docs/playbook/DECISIONS.md)。

## 4. 怎么开始

### 第一步：取得仓库

这是私有仓库。同学需先获得仓库访问权限，并在自己的电脑登录有权限的GitHub账号。

```bash
git clone https://github.com/ada-c38f0bb79f/logistics-load-planner.git
cd logistics-load-planner
```

已经在现有项目目录工作的人不必重新克隆。先检查本地修改；工作区干净且在正确分支上时，可用 `git pull --ff-only` 同步。不要覆盖或清除他人尚未提交的工作。

### 第二步：按顺序读最小必要材料

1. 阅读 [START_HERE.md](START_HERE.md) 和 [AGENTS.md](AGENTS.md)。
2. 阅读 [STATE.md](docs/playbook/STATE.md)，确认当前事实。
3. 查看 [board.json](docs/playbook/board.json)，只领取依赖已完成的任务。
4. 阅读 [DECISIONS.md](docs/playbook/DECISIONS.md) 和当前任务卡列出的必读材料。

不必一次把所有文档和历史聊天都交给模型。一个任务的必要上下文是：项目约定、当前进度、当前任务卡，以及卡片引用的规格。

### 第三步：运行当前可用的自检

在仓库根目录执行，需要可用的Python 3，无需安装第三方库：

```bash
python scripts/check_playbook.py
```

初始化状态下，输出应包含：

```text
PASS: 26 task cards; acyclic dependencies; 3 UI example pairs consistent.
Ready tasks: B01, F01
This verifies planning artifacts only; no application or solver tests were run.
```

随着任务状态变化，Ready tasks会变化，这是正常现象。检查失败时按报错修复状态、依赖或示例，不能删除检查来制造通过。

**当前尚无业务应用启动命令。** 任务卡中的后端测试、服务启动和前端构建命令是对应任务实现后的验收目标，不表示现在已经能运行。B01/F01完成后，应把实际安装、启动命令补入本README。

### 第四步：两条线同时开工

| 分工 | 从哪里开始 | 负责范围 |
| --- | --- | --- |
| 主线开发者与模型 | [B01：建立后端骨架](docs/playbook/tasks/B01.md)，之后按依赖做B02等任务 | 数据、后端、算法、独立校验、实验和技术文档 |
| 前端同学与其模型 | [F01：搭建前端及协议类型](docs/playbook/tasks/F01.md)，然后F02→F03→F04 | 前端、路线和3D展示、交互、演示素材 |
| 项目负责人 | 核对比赛通知、协调分工、试用验收 | 精确截止时间、提交入口、团队信息和最终提交 |

F01可以直接使用接口示例，无须等后端。前端做到F04后，等待B13真实接口完成，再执行F05联调。

主线负责 `backend/`、`tests/`、`scripts/`、`data/`、`docs/` 和根配置；前端负责 `frontend/`。其中尚不存在的目录由对应任务创建。主线统一维护任务状态表，前端通过交接报告提供完成证据，避免双方同时修改同一状态文件。

### 第五步：每次只完成一个可验收任务

1. 检查任务卡的依赖是否全部完成，并查看已有代码，避免重复开发。
2. 在状态表记录负责人，将任务设为 `in_progress`。
3. 按卡片步骤实现，只修改相关范围。
4. 实际运行验收，保存命令、结果、截图或输出文件。
5. 将证据写入 `artifacts/evidence/<任务ID>.md`，并在状态表引用该路径。
6. 通过后标记 `done`；未通过则保留 `in_progress` 或标记 `blocked` 并写明原因。
7. 更新当前进度并按接力格式报告，再领取下一张依赖已满足的卡。

“代码写了”“界面看起来正常”“模型说完成”都不能替代验收证据。文档准备完成也不能把开发任务标为done。

## 5. 直接交给模型的提示词

### 通用接力

> 先读 START_HERE.md、AGENTS.md 和当前进度。领取一个依赖已完成的任务，按任务卡实现并执行验收，保存真实证据后更新状态。不要重新设计架构，不把示例数据当算法成果；未通过验收不能标记完成。

### 主线第一次开始

> 请从 B01 开始。先读取项目入口、开发约定、当前进度及 B01 任务卡，检查环境与已有文件，再建立后端骨架。完成后运行卡片要求的验证，保存真实证据并更新任务状态。当前只完成 B01，不提前扩展其他功能，不修改同学的前端代码。

### 发给前端同学或其模型

> 请负责本项目 frontend 目录。先读 START_HERE.md、设计决策、接口协议和 F01 任务卡。用 docs/playbook/examples 中的JSON从 F01 开始，依次完成 F02、F03、F04；B13完成后再做F05真实联调。界面必须标明演示数据，箱体按响应坐标绘制，不硬编码优化收益。接口变更先与主线同步，每张卡完成后提交修改文件、启动命令、验收证据和当前问题。

换模型或修复失败任务时，使用 [HANDOFF.md](docs/playbook/HANDOFF.md) 中对应提示词。无需让下一模型重新猜测项目目标。

## 6. 两天怎么推进

| 阶段 | 主要工作 | 阶段验收 |
| --- | --- | --- |
| 第一天上午 | 环境、模型、数据、接口示例；前端骨架 | 数据格式一致，前端可读取示例 |
| 第一天下午至晚间 | 路线、几何、卸货、独立校验、配载与修复；前端3D | 至少一个真实算法闭环，失败有原因 |
| 第二天上午 | HTTP接口、真实联调、解释 | 从页面提交到结果展示完整跑通 |
| 第二天下午 | 回归、对比实验、演示和文档 | 结果可追溯，材料与代码一致 |
| 截止前至少90分钟 | 冻结功能、干净环境复现、提交检查 | 能独立运行，提交事项逐项核对 |

具体依赖和缩减顺序见 [SCHEDULE.md](docs/playbook/SCHEDULE.md)。时间不足时先减少动画、可选模型能力和额外图表；不能通过删除硬约束校验来宣称完成。

## 8. 样例、算法结果和实验的区别

- **接口样例**：手工构造，响应中 `is_mock=true`，用于前端开发与字段校验。
- **模拟数据上的真实求解**：服务应返回 `is_mock=false`，但 `data_source=synthetic`，说明算法确实运行，输入仍是模拟业务数据。
- **正式实验结果**：保留输入、配置、原始响应、独立验证与环境信息，按统一口径进行比较。

成本改善率只能在双方均有效且服务相同门店集合时比较。少配送订单带来的费用减少不能算降本；未实测的企业收益只能作为待验证目标。
