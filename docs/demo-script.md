# 3 分钟演示脚本

准备：三服务已启动（8000 / 8001 / 5173），浏览器打开 http://127.0.0.1:5173，案例下拉可见「求解服务案例」。窗口 1440 × 900。

| 时间 | 画面 | 旁白要点 |
|---|---|---|
| 0:00–0:20 | 顶栏与空白工作台 | 连锁药店中心仓每天向几十家门店配送几百个 SKU。调度员要同时决定派哪辆车、走什么顺序、箱子怎么摆、到店怎么卸。现在靠经验，装不下、卸不出来都是到现场才发现。 |
| 0:20–0:40 | 选「服务案例 standard-11」，左栏显示 30 家门店、112 箱、12 辆车 | 输入是订单、门店时间窗、车辆尺寸与载重。这里是模拟数据，字段与真实业务一致。 |
| 0:40–1:30 | 点「运行求解」→ 约 1 秒出结果；右栏「全部配送」、独立校验通过；左栏点 V01；中间 3D 车厢；点「下一步」两三次；切「路线示意」 | 求解器一次给出三样东西：每辆车的路线和到站时刻、每个箱子在车厢里的坐标、按到站顺序的卸货步骤。后门在黄黑条这一侧，先送的箱子靠门。右边的「独立校验」是另一套代码重算了边界、碰撞、承托、易碎、时间窗、卸货是否被挡，不信求解器自己说的。 |
| 1:30–2:10 | 右栏调度助手：点「总览」→ 显示「模型 deepseek-chat · 已核对 N 个数字」；输入「V02 今天不出车」→ 解析 → 显示「车辆 V02：可用 → 移除」→ 点「确认并重新求解」→ 自动对比表 | 大模型在这里只做两件事：把结果解释给人听，把人的话变成修改建议。每个数字都在服务端事实表里核对过，编的数字会被拦下来。修改建议必须人点确认才会送去求解，模型不碰任何坐标和分配。重算后自动对比：同样 10 家门店，4 辆车变 3 辆，费用可比才给百分比。 |
| 2:10–2:40 | 选「服务案例 c02」→ 运行 → 「部分配送」，左栏红色「S01 箱件尺寸超过所有车厢」 | 装不下的不会被悄悄丢掉：明确列出门店、原因码、消息。总体积够但单件尺寸不合，这是只看体积的系统会漏的。 |
| 2:40–3:00 | README 实验表 / 架构图 | 三个进程、两份 JSON 协议，模型可换成企业私有部署，离线也能跑。落地路径：历史订单离线验证 → 调度员影子试用 → 人工确认后执行。 |

录制建议：headless 自动化脚本 `_tools/shot_flow.mjs` 可生成同一流程的截图；人工录屏时按上表顺序操作即可，不要提前准备好结果。
