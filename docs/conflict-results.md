# O02 冲突案例对照结果

运行日期：2026-10-10。实验输入：`data/conflict_cases/manifest.json` 中预先登记的 19 案；原始输出：`artifacts/benchmarks/o02-conflict-20261010/`。运行时工作区有本轮未提交代码，基础 HEAD 为 `b84a592`；精确实现文件 SHA-256 见实验 `manifest.json`。案例均为**合成场景**，不是企业订单或经济收益。

## 最关键的结论

在 5 个组合几何和 5 个几何/时间窗联动案例中，原 greedy 与 sequential 分别完成 0/10 和 5/15 店；coupled 完成 10/10 和 15/15 店，并各有 5 次真实、已验证的接受动作。初始路线的装载失败和搬移过程可在逐次 `response.json.repair_trace` 核对。

**但是实验专门增加的 `sequential_reinsert` 简单补救基线也完成同样的 25/25 店，且逐案例费用与 coupled 完全相同。** 因此这组实验支持“失败后反馈修复能恢复服务”，尚不支持“当前 coupled 比简单失败后重新插入更好”。不能将服务集合不同的 sequential 与 coupled 成本直接算改善率。

另外 5 个卸货机制控制例的预置坏布局均被 `UNLOAD_BLOCKED` 拒绝，同时各有独立可行布局；四种端到端方法在这些输入上均直接找到全覆盖方案，**协同修复触发数为 0**。这是卸货校验与预防能力的证据，不是“卸货冲突经协同修复”的证据。2 个原有无修复控制例仍全覆盖，2 个尺寸确证不可行控制例均未被伪装为已配送。

## 方法与可比性

每案用同一落盘 SolveRequest；greedy、sequential、coupled 走公开 `options.method`；`sequential_reinsert` 是**仅实验内部**的适配器，输入 JSON 的 `options.method=sequential`，运行后在保留已成功路线的前提下，按时间窗/ID 对未分配门店做费用增量排序的重新插入，复用相同 packer 与独立校验器。它不是公开 API 的第四个方法。四种方法均使用请求中的同一时间与迭代预算。

开发探针使用 seed 11，期间为使车型容纳候选箱件，把时间联动场景目标车长度由 5000 调至 5100 mm；该探针与正式输出分开保留在 `artifacts/benchmarks/o02-development*/`。正式变体在 seed 22/33/44/55/66 上一次性生成并按 manifest 全部运行，另外两条不可行控制为 77/88。5 个变体是固定公式变化，并非独立真实订单；也未用于证明统计显著性。

费用仅在同案已服务门店 ID 集合相同、双方独立有效且基线费用大于零时计算。57 个 coupled 对照中：相对 greedy、sequential 各 7 个可比、12 个不可比；相对 reinsert 17 个可比、2 个基线成本 0 不可比。可比的 reinsert 对照改善率全部为 **0%**。各方法最终有效方案卸货阻挡数为 0。

## 下一步判断

O03 不能仅凭当前结果宣称提升：10 个修复案例与简单 reinsert 仍完全相同。若继续做预算内择优搬移，需要先设计明确的“首个可行候选比后续候选贵”案例，比较两者有效服务集合和费用；若要突出卸货反馈，则需找到真实端到端触发修复的顺序冲突，不能把预置阻挡布局当成求解器修复成果。无上述证据时，当前较稳妥的创新表述是**联合可执行性校验、修复过程可追溯、受控自然语言调整**。
